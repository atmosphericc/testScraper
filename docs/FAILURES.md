### [2026-05-11 PM7] - Cross-Cutting Concerns: 5 Fixes - Walmart
**Symptom**: Post-PM6 audit identified five issues that span multiple files and don't fit a single-file audit pattern: (a) session-restart hygiene (`_run_purchase`'s browser-restart path left lots of stale state); (b) deprecated `asyncio.get_event_loop()` call that silently misbehaves on Python 3.12+; (c) unguarded read-modify-write of GraphQL hash globals from CDP threads; (d) unbounded activity-log growth. None had fired hard in production, but each was a latent issue with concrete failure modes if exercised.
**Root Cause**:
1. **`session_manager.stop()` left restart-tainted state**: after `_run_purchase`'s auto-restart called `_session.stop() → _session.start()`, the following stale state remained: harvester task still running (would keep trying to access `self._page` which is briefly None), `_pending_graphql` + `_pending_graphql_tab2` full of request IDs from the dead browser (collision risk with new IDs), `_live_cookies` cached from before crash (workers would use cookies that no longer match the new browser's TLS fingerprint), `_px3_timestamp` not reset (`needs_rewarm()` returned False so post-restart re-warm was skipped), `_monitor_cookie_snapshot` pointed at cookies from the dead context, and `_last_validation_result` cached True from before crash (next validate_session call within `SESSION_VALIDATE_INTERVAL` would return the cached True even though the session might be logged out).
2. **Harvester never restarted after session restart**: `start_harvester` was called exactly once in `purchase_manager.start()`. The session-restart branch in `_run_purchase` called `_session.start()` to create a new browser but no one called `start_harvester` again. Post-PM7-fix-1, `stop()` cancels the harvester task — without the new fix #2, restart would result in NO harvester running, no _px3 refresh, and the next stock check would BLOCK on a stale cookie.
3. **`asyncio.get_event_loop()` is deprecated** since Python 3.10. On 3.12+ it raises `DeprecationWarning` and returns a NEW loop when no loop is running, which would silently misbehave if `start()` were ever called outside an await context (e.g. test harness, edge-case shutdown handler).
4. **`config.set_graphql_hash_atf/btf` read-modify-write race**: CDP `RequestWillBeSent` handlers fire on zendriver's internal thread pool. Two concurrent handlers seeing different hash values can both pass the `if current != new` check, both write to the module global, both log the INFO line. Last writer wins; the other value is silently discarded. Hash values are normally stable so this is rarely exercised in practice, but during a stale-hash refresh (when Walmart deploys a new hash) we DO see different intercepts come in close succession.
5. **`WalmartLogger._activity_log` unbounded growth**: every `log_activity` / `log_error` call appended one dict and called `_save_activity_log()` which pickles the entire list. The list had no cap. A long-running bot accumulates thousands of entries (status callbacks fire on every monitor tick, every state change, every purchase step). Eventually each pickle write becomes multi-MB, the lock-held write window grows, and concurrent activity-log readers block longer.
**Fix Applied**:
1. `session_manager.stop()` extended: calls `stop_harvester()` early (cancels the task before nulling `_page`), then under their respective locks clears `_pending_graphql` + `_pending_graphql_tab2`, sets `_live_cookies = {}` + `_live_cookies_timestamp = 0.0` + `_px3_timestamp = 0.0` + `_monitor_cookie_snapshot = []`, and resets `_last_validation = 0.0` + `_last_validation_result = False`. Each step independent — no single failure aborts the rest.
2. `purchase_manager._run_purchase` session-restart branch now calls `self._session.start_harvester(self._loop)` after the post-restart validate_session succeeds and the new page is wired into the monitor. Wrapped in try/except so harvester restart failure doesn't abort the purchase attempt (just logs the issue).
3. `purchase_manager.start()` switched to `asyncio.get_running_loop()` with a `RuntimeError` fallback to `get_event_loop()` for any caller running outside an await context. Comment added explaining why.
4. `config.py` added module-level `_graphql_hash_lock = threading.Lock()`. Both setters acquire it for the read-modify-write block; both getters acquire it for the read (so a partial reassignment can't be observed). Empty-value guard moved outside the lock to skip lock acquisition for the no-op case.
5. `logging_manager.py` added `ACTIVITY_LOG_MAX_ENTRIES = 2000` class constant. `__init__` trims on load. Both `log_activity` and `log_error` append-paths trim if length exceeds the cap.
**Confidence**: high (1-3, 5 — verified by AST + targeted smoke tests including stop()-then-state-check, hash setter round-trip, and a synthetic 20-message append against a cap-5 logger); medium-high (4 — lock is correct but no live thread-pool concurrency test was run).
**Outcome**: Browser restart now produces a clean session — harvester restarted, stale state cleared, validation re-runs. Python 3.12+ doesn't emit deprecation warnings on every manager start. GraphQL hash setters no longer lose values under concurrent CDP interception. Activity log can't grow without bound. Files: `walmart/session_manager.py`, `walmart/purchase_manager.py`, `walmart/config.py`, `walmart/logging_manager.py`.

### [2026-05-11 PM6] - Deep Audit of 4 Largest Walmart Files: 9 Fixes - Walmart
**Symptom**: Pre-run deep audit of `queue_handler.py`, `purchase_manager.py`, `session_manager.py`, `purchase_executor.py` (the four files that received only surface fixes in prior rounds — together ~4700 lines of the most-critical code paths). Surfaced an outright NameError (would crash the harvester loop on first env-var check), a silent cookie-domain-mismatch bug (could overwrite the saved Walmart session with Google cookies), a session-state cache that masked logout failures, a state-machine bug that permanently stuck items in PURCHASING, and several missing `asyncio.wait_for` wrappers that could freeze the purchase flow indefinitely.
**Root Cause**:
1. **`walmart/queue_handler.py:enter_queue`** — `await self._page.get(item_url)` without `asyncio.wait_for`. The other queue methods (detect/join/wait_for_passthrough) all have their own loops with deadlines, but the entry navigation could stall on a slow/blocked redirect and freeze the entire queue flow. Same class of bug PM closed for cart navigations in `purchase_executor`.
2. **`walmart/queue_handler.py:_check_passthrough_widget`** — two of the four CSS patterns at line 350 were `'button:has-text("Join queue")'` and `'button:has-text("Hold my spot")'`. `:has-text()` is patchright-specific; zendriver's `query_selector_all` silently fails on it and the exception is swallowed by the `except: continue`. Dead selectors that produced no visible error but contributed nothing to detection.
3. **`walmart/purchase_manager.py:_on_stock_change`** — only `_in_stock_ids.add(item_id)` paths existed in the codebase; `.discard()` was never called when an item went OOS. The priority-override branch in `_on_in_stock_signal` reads `_in_stock_ids` to decide which currently-in-stock product to buy when a high-priority item is also available. A long-OOS item that was briefly in-stock would forever be a priority-override candidate, potentially redirecting purchases to an item that hasn't been buyable in hours.
4. **`walmart/purchase_manager.py:_on_in_stock_signal` priority-override** — at line 255 the method sets `self._state[item_id] = PURCHASING` for the triggered ID. Lines 285-289 then potentially override `item_id` to a higher-priority product and mark THAT new ID as PURCHASING. But the *original* item_id was never reset from PURCHASING back to MONITORING. Since the early-return at line 232-234 skips signals for items already in PURCHASING/IN_QUEUE/SUCCESS, the original item was now permanently locked out — no future in-stock signal for it would ever process.
5. **`walmart/purchase_manager.py:_is_monitor_healthy`** — reached into `self._monitor._running_lock` + `self._monitor._running` private attrs. The monitor has a public `is_healthy()` method that does exactly this; the private-attr access broke encapsulation and could silently fail if the monitor renamed those internals.
6. **`walmart/session_manager.py` missing `import os`** — line 971 (`_rewarm_env = os.environ.get("WALMART_REWARM_PAGES", _default_rewarm)`) used `os` but the import list didn't include it. Latent NameError — would fire the first time the harvester checked the env var. Probably masked by never actually exercising that code path under the configured env.
7. **`walmart/session_manager.py:validate_session`** — the cache check at line 569 short-circuited to `return True` if a validation had run within `SESSION_VALIDATE_INTERVAL`, regardless of that validation's actual outcome. So if `validate_session` returned False at T0 (missing auth cookie), the next call at T0+1s would return True — masking the logged-out state for up to the cache window. Both the manager's startup path AND the per-purchase restart path call this, so the masked-False could cause the manager to believe a dead session was still valid.
8. **`walmart/session_manager.py:save_cookies`** — used `cdp.network.get_cookies()` which is URL-filtered to the current page's origin. `warm_session` deliberately leaves Tab 1 on an external warmup site at the end (Google/Amazon/Reddit) before `return_tab1_to_walmart` brings it back; if any `save_cookies()` call happened during that window, the saved file would be overwritten with the external site's cookies, wiping the Walmart session on disk. Other call sites in the same file use `get_all_cookies()` (the all-domains variant) — `save_cookies` was the only outlier. Also: the write was not atomic — same crash-safety gap PM3 fixed for `walmart_config.json` and `purchase_states.json`.
9. **`walmart/session_manager.py` Tab 2 GraphQL handler asymmetry** — Tab 1's handler registration (lines 335-342) included both `RequestWillBeSent` and `LoadingFinished`. Tab 2's (lines 405-410) registered only `RequestWillBeSent`. The pattern is: `RequestWillBeSent` puts the request_id into `_pending_graphql`, `LoadingFinished` pops it and triggers the body fetch. Without `LoadingFinished` on Tab 2, request_ids captured on Tab 2 leaked into `_pending_graphql` forever AND their bodies were never fetched. Additionally `_fetch_graphql_body` hardcoded `self._page` (Tab 1) for the body fetch, so even if `LoadingFinished` HAD been registered on Tab 2, asking Tab 1 for a Tab-2-captured request_id would silently return empty.
10. **`walmart/purchase_executor.py`** — five `await self._page.get(...)` calls in critical paths (`_navigate` two times, `_cart_and_checkout` two times, `_go_to_checkout` post-/blocked re-nav, `_is_item_already_in_cart` back-to-product nav) had no `asyncio.wait_for` wrapper. A stalled navigation could freeze the purchase loop indefinitely. PM had wrapped only the three `_clear_cart` family calls in this same pattern.
**Fix Applied**:
1. `queue_handler.py:enter_queue`: wrapped `self._page.get(item_url)` in `asyncio.wait_for(..., timeout=15.0)`. On timeout, logs and returns False so the manager's `_run_purchase` flow can proceed to its own failure-handling path.
2. `queue_handler.py:_check_passthrough_widget`: dropped the two dead `:has-text(...)` patterns from the CSS-pattern fallback loop. Pure CSS-attribute patterns remain. Removed unreachable `return False` after `while True` in `wait_for_passthrough`.
3. `purchase_manager.py:_on_stock_change`: added `_lock`-guarded `_in_stock_ids.discard(item_id)` on the OOS branch and `.add(item_id)` on the in-stock branch (the latter was already done in `_on_in_stock_signal` but adding it here too is idempotent and ensures the set tracks the monitor's view even when no purchase fires).
4. `purchase_manager.py:_on_in_stock_signal`: stash the triggered `item_id` as `original_item_id` BEFORE the override block. After the override picks a different target, under the same `_lock` acquisition that marks the override target as PURCHASING, reset `original_item_id` back to MONITORING (only if it was PURCHASING — defensive check). Also cleaned up the dead `hasattr(self, '_in_stock_ids')` check at line 266 — the attribute always exists since __init__.
5. `purchase_manager.py:_is_monitor_healthy`: replaced private-attr access with `self._monitor.is_healthy()`. Added `if not self._running: return` early-return guard to `stop()` for idempotency. Moved `import random` from inside `_compute_test_loop_cooldown` to top-level imports.
6. `session_manager.py`: added `import os` to the import block. Verified by AST + by exercising the harvester env-var code path under smoke test.
7. `session_manager.py:validate_session`: added `self._last_validation_result: bool` to __init__. Cache check returns `getattr(self, "_last_validation_result", True)` instead of unconditional True. All return paths update both `_last_validation` and `_last_validation_result`. Exception path does NOT update (retry on next call). Defensive `getattr` default of True preserves prior semantics for any caller that constructs a manager without exercising __init__.
8. `session_manager.py:save_cookies`: switched to `cdp.network.get_all_cookies()`. Wrapped the file write in the same tempfile + `os.replace` atomic pattern PM3 applied to config + purchase_states. fsync the tempfile before replace; best-effort tempfile cleanup in finally for the exception path.
9. `session_manager.py`: added `_pending_graphql_tab2: dict` (separate from `_pending_graphql`). Added `_on_network_request_tab2` / `_on_loading_finished_tab2` that route through the new dict. Common logic moved to `_enqueue_pending_graphql(event, pending)` and `_schedule_body_fetch(event, pending, page)` private helpers. Tab 2 now registers BOTH handlers. `_fetch_graphql_body` takes an optional `page` parameter (defaults to `self._page` for backward compat). Stored values changed from `item_id` to `(item_id, enqueue_time)` so a `_pending_max_age_seconds = 30.0` opportunistic prune on each new enqueue can drop entries that never completed (cancelled navigation, network abort, etc.).
10. `purchase_executor.py`: all six remaining navigations wrapped in `asyncio.wait_for` with 15-20s timeouts. Each TimeoutError path either returns False, logs and continues, or sets the poisoned-session flag — matching the pattern PM established for the cart-clear family. AST verified by `grep` showing 0 remaining unwrapped `self._page.get(` calls.
**Confidence**: high (1-6, 8, 10 — verified by AST + smoke test + targeted unit-style asserts); medium-high (7 — cache state machine is correct but only fully exercised with a real Walmart session); medium (9 — dual-tab routing is correct in code but only one tab actually intercepts GraphQL in practice today; the fix is largely defensive for when Tab 2 starts being used as a stock-check tab).
**Outcome**: Queue-entry stalls can no longer freeze the purchase flow. Long-OOS items can no longer be selected by priority-override. Original items can no longer be permanently stuck PURCHASING after a priority-override. The harvester loop no longer NameErrors on first env-var check. Logged-out sessions are detected within `SESSION_VALIDATE_INTERVAL` instead of being masked by stale cache. `save_cookies` can no longer overwrite the Walmart session file with cookies from an external warmup site. Tab 2 GraphQL intercepts no longer leak memory or lose stock data. All purchase-flow navigations have crash-safe timeouts. Files: `walmart/queue_handler.py`, `walmart/purchase_manager.py`, `walmart/session_manager.py`, `walmart/purchase_executor.py`.

### [2026-05-11 PM5] - Remaining Walmart Files Audit: 11 Fixes - Walmart
**Symptom**: Pre-run sweep of the four Walmart files not yet audited this campaign (`stock_check.py`, `proxy_manager.py`, `blueprint.py`, `self_healing_agent.py`). None of the bugs found had fired hard in production yet, but several were latent timebombs — particularly the self-healing agent's overly-broad regex (would auto-patch code on a 404 page) and the proxy manager's silent double-release (which permanently miscounts the semaphore).
**Root Cause**:
1. **`walmart/stock_check.py:184`** — `check_items()` calls `parse_cookies(COOKIES_RAW)` but `COOKIES_RAW` is not defined anywhere in the file. Would `NameError` immediately. The header docstring already says cookies come from the persistent profile via `load_cookies()` — `check_items` was simply never updated to match. Dev-only tool (never imported by prod), but broken for an unknown amount of time.
2. **`walmart/proxy_manager.py:_ProxyStats`** — `self.total += 1` is not atomic in CPython for instance attribute mutation (it's LOAD_ATTR + BINARY_ADD + STORE_ATTR). Monitor workers and the dispatcher concurrently call `record_success/record_error`, so counts can be lost. `error_rate()` reads `total` + `errors` without coordination, can see inconsistent intermediate states.
3. **`walmart/proxy_manager.py:_stats = defaultdict(_ProxyStats)`** — `defaultdict`'s create-if-missing is not atomic across threads. Two concurrent first-callers for the same proxy can each instantiate a fresh `_ProxyStats`; whichever STORE_SUBSCRIPT lands last wins, silently discarding the other thread's counts.
4. **`walmart/proxy_manager.py:release_checkout_proxy`** — original gate was `if proxy not in self._checkout_available: append + semaphore.release`. Legitimate single release: gate True → release, fine. Double release: second call sees proxy is now IN available → gate False → silent no-op (no log either). But if a different caller mistakenly calls release on a proxy they never acquired, the gate fires and the semaphore is released anyway — over time the semaphore count drifts upward, eventually allowing more concurrent acquires than there are proxies in the pool.
5. **`walmart/blueprint.py`** — same lifecycle gaps PM2 closed in `walmart_app.py`: no shutdown handler, `/api/status` + `/health` + `/` index routes called `_manager.get_status()` with no try/except. A transient state-corruption mid-shutdown crashes the 15s dashboard polling and triggers the SSE reconnect storm. The unified-app variant inherited these because the morning audit was explicitly scoped to `walmart_app.py` only.
6. **`walmart/self_healing_agent.py:LogDiagnostician._RULES` WRONG_SELECTOR regex** — `r"not found|no.*button|selector.*not|element.*not|locator.*not|no_atc|no_checkout|no_place_order"`. The `not found` prefix matches "Page not found" (404 responses), "Product not found in database", "Order not found", etc. The `no.*button` matches "no button work needed". The `element.*not` matches "element is not visible". Any of these would push the recovery loop down the `_handle_wrong_selector` path, which auto-mutates `purchase_executor.py` and `queue_handler.py` based on whatever HTML happened to be captured — potentially permanently breaking selector lists.
7. **`walmart/self_healing_agent.py:_capture_page_html`** — calls `session.get_page()` which returns Tab 1 (the harvester). Tab 1 is on homepage/category pages, never on the failed buybox / checkout / place-order screen. The HtmlSelectorPatcher would scan an irrelevant page, find 0 candidates, log "no confident match", and skip — meaning the agent never actually auto-healed anything.
8. **`walmart/self_healing_agent.py:_run_manager_with_recovery`** — no maximum restart limit. If patches don't fix the underlying issue, the agent restarts every `RESTART_DELAY=15s` indefinitely. On a hard Akamai block this burns through proxy reputation and triggers escalation by Walmart's WAF.
9. **`walmart/self_healing_agent.py:HtmlSelectorPatcher._FILE_MAP`** — `ATC_SELECTORS` maps to `"purchase_executor.py"` only. But `ATC_SELECTORS` is also defined in `walmart/queue_handler.py:87` (the AM-round audit added this for queue pass-through detection). Auto-patching only the executor copy leaves the queue handler stale — exactly the drift bug the AM round fixed manually.
**Fix Applied**:
1. `stock_check.py:184`: replaced `parse_cookies(COOKIES_RAW)` with `load_cookies()`. Kept the unused `parse_cookies` helper since it's a public function someone might call from a notebook.
2. `proxy_manager.py:_ProxyStats`: added internal `_lock` (threading.Lock). `record_success/record_error/error_rate` all acquire the lock; `is_benched/bench` are plain float read/write and don't need locking (CPython atomic).
3. `proxy_manager.py`: added module-level `_stats_lock` + new `_get_stats(proxy)` helper. All `self._stats[proxy]` accesses now route through `_get_stats`. `stats_summary` snapshots the dict under the lock to avoid `RuntimeError: dictionary changed size during iteration`.
4. `proxy_manager.py:release_checkout_proxy`: inverted the gate logic. Now checks `if proxy in self._checkout_available: WARN double-release, return` first. If not already in available, append + release semaphore exactly once. Calling release on a proxy not in the checkout pool is a DEBUG-level no-op. Tested: double-release produces exactly one WARN and never releases the semaphore twice.
5. `blueprint.py`: new `stop_manager(timeout=5.0) -> bool` exposed publicly. `start_manager()` now stores the loop in `_manager_loop` module global and auto-registers `stop_manager` via `atexit`. `/api/status` + `/health` + `/` index routes all wrap `_manager.get_status()` (and `get_activity_log()` where applicable) in try/except with explicit error envelope. NOTE: `atexit` does NOT run when `app.py`'s Target shutdown handler calls `os._exit(0)` — fully reliable shutdown requires the operator to wire `stop_manager()` into `app.py`'s `shutdown_handler`, but that edit is out of Walmart-only scope.
6. `self_healing_agent.py:_RULES`: WRONG_SELECTOR rule tightened to specific phrases the executor actually emits: `\bno_atc\b`, `\bno_checkout\b`, `\bno_place_order\b`, `\bno_cvv\b`, `ATC button not found`, `checkout button not found`, `place order button not found`, `cvv field not found`. The broad `not found` and `no.*button` patterns are gone. Verified by unit test: "Page not found 404" → UNKNOWN, "product not found" → UNKNOWN, "no_atc" → WRONG_SELECTOR.
7. `self_healing_agent.py:_capture_page_html`: now calls `session.get_checkout_page()` first (Tab 2 where failures happen). Falls back to `session.get_page()` (Tab 1) only if Tab 2 is unavailable. Catches AttributeError on `get_checkout_page` so the agent still works against older session_manager versions.
8. `self_healing_agent.py`: added `MAX_RESTARTS_PER_HOUR = 8` + rolling-window `_restart_history` deque. Before each restart, prunes timestamps older than 1h and stops the recovery loop if the window is full. Logs a clear `[HEALER] Restart-rate breaker — N restarts in last hour exceeds limit` line.

Other entries (CHECKOUT, PLACE_ORDER, CVV, QUEUE_ENTRY) wrapped in `[...]` for consistency.
**Confidence**: high (1-4, 6, 9 — straightforward changes verified by AST + smoke tests); medium-high (5 — atexit fallback works for clean exits but not the `os._exit` path; documented); medium (7 — `get_checkout_page` may return None when checkout tab not yet created, fallback to Tab 1 handles this); high (8 — rolling window pattern is standard).

ATC selector auto-patches cover both files. Files: `walmart/stock_check.py`, `walmart/proxy_manager.py`, `walmart/blueprint.py`, `walmart/self_healing_agent.py`.

### [2026-05-11 PM4] - stock_monitor.py Concurrency Audit: 6 Latent Races - Walmart
**Symptom**: Pre-run audit of `walmart/stock_monitor.py` (the only Walmart file with NUM_DISPATCHERS=3 concurrent threads sharing mutable state) surfaced six race conditions and a session-teardown crash path. None had fired hard in production yet but each was a latent bug that would surface either (a) when a real high-demand drop produced a burst of BLOCKED/400/429 responses across multiple dispatchers in the same window, or (b) during shutdown if a dispatcher was mid-fetch when the session cleared its browser reference.
**Root Cause**:
1. **`_consecutive_blocked` increment race**: Three dispatcher threads concurrently processed BLOCKED results. `self._consecutive_blocked += 1` is not atomic in CPython for instance attributes (the LOAD_ATTR, BINARY_ADD, STORE_ATTR sequence can interleave). Worse, the "trip once per cooldown" gate (`current >= threshold and not already_open`) read `_monitor_circuit_open_until` without a lock; two dispatchers could both see "not open" and both write `_monitor_circuit_open_until = monotonic() + 120`, producing duplicate "circuit breaker tripped" log lines, duplicate dashboard status messages, and (more concerning) duplicate calls to `_log_px3_state_on_block` which each spawned a parallel CDP coroutine on the same browser page — meaning two `cdp.network.get_all_cookies()` calls in flight simultaneously through one tab.
2. **Cooldown finalizer race (line 427-432 in pre-patch)**: When the breaker tripped, all 3 dispatchers waited the full pause, then each independently set `_consecutive_blocked = 0`. Three resets — harmless for the counter value, but the wait-and-resume pattern meant all 3 dispatchers fired their next batch within ~1ms of cooldown end, producing a synchronized burst that is itself a strong Akamai signal.
3. **`_rate_limit_hits` lock confusion**: The increment ran under `self._checks_lock` (which guards `_total_checks` and `_total_errors`, not the rate-limit fields), and `_rate_limit_backoff` was read+written without any lock. Same trip-gate issue as the BLOCKED counter — multiple dispatchers could each set the backoff timestamp.
4. **`_rate_limit_hits` never resets**: Counter incremented monotonically. After the first backoff fired at hits=3, the next transient 429 immediately re-tripped the gate (still at 3). No reset path existed.
5. **`_trigger_graphql_hash_refresh` log/signal spam**: A batch of N products that all returned HTTP 400 produced N ERROR-level log lines and N flag-sets within ~50ms. The harvester only needs one signal — and the ERROR log is alarming enough that 5 of them in 50ms looks like a real outage when it's actually one stale hash affecting all products.
6. **`_run_browser_fetch` / `_log_px3_state_on_block` shutdown race**: Both functions check `self._session._page is not None` and then dereference it inside an `async def` closure submitted via `run_coroutine_threadsafe`. Between the check and the coroutine actually running, `WalmartSessionManager._page` can be cleared (session_manager.py:360, 431 — runs on shutdown). The coroutine then dereferences `None.evaluate(...)` / `None.send(...)`, raising `AttributeError` inside the future. Caught by the outer try/except but produces noisy "future error" lines instead of clean "session shut down".
**Fix Applied**:
1. **`_cb_lock = threading.Lock()`** added (line 106). Guards `_consecutive_blocked`, `_monitor_circuit_open_until`, and new `_graphql_refresh_signaled`. All BLOCKED-counter reads/writes + the threshold-trip decision happen under this lock in a single critical section. Non-BLOCKED reset is also under the lock so it cannot interleave with the BLOCKED increment.
2. **Cooldown finalizer rewritten** with a witness pattern (lines 437-456): snapshot `cb_open_until` under the lock, wait outside the lock, then under the lock re-check `if self._monitor_circuit_open_until == cb_open_until` — only the first dispatcher to observe the cooldown ending resets the counter and clears the open-until.
