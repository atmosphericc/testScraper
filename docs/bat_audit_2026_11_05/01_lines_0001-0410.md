# Audit: run_bot_with_nightly_restart.bat, lines 1-410

Audited 2026-11-05. Source: `run_bot_with_nightly_restart.bat` (lines 1-410 only; line 410 ends mid-comment inside the "CHECKOUT FAST LANE" block, which continues in the next chunk). Code greps cover `src/`, `app.py`, `tools/`, and repo-root `*.py`.

All dated claims about Target's anti-bot behaviour below ("HUMAN walled the BD range on 09-07", "Shape blocks BD-IP logins", etc.) are the operator's own observations at the cited date. They may be stale and are reported as history, not current fact.

## 1. Overview

This range is the top of the launcher: the header, Python-venv autodetect, and then the bulk of the "arming" configuration for two subsystems. (a) The stock-detection side (the "resilient" RedSky sweep: how fast it polls Target's inventory API, which API channel it uses, how it backs off when Target's anti-bot layers captcha or rate-limit it). (b) The identity and fingerprint side (how each Chrome profile presents itself, so Target's bot-defence vendors F5 Shape and HUMAN/PerimeterX do or do not flag it), plus the first group of purchase-retry knobs (add-to-cart retry caps, delay timing, a circuit breaker, logging taps). Nearly every flag carries a dated REM paragraph recording the incident that caused it, so this range doubles as an incident log. The restart loop itself is NOT in this range; only the environment setup is.

## 3. Narrative by section

### 3.1 Header, venv, stack (lines 1-38)
The wrapper relaunches `app.py` if it crashes, with no timed cutoff; Ctrl+C causes a clean exit code 0 and the wrapper stops (2026-09-15 fix). The venv autodetect exists because pointing at a broken/missing interpreter caused two incidents (05-22 broken `venv\`, 06-04 absent `.venv\`). Risk if wrong: bot silently not running on drop night (availability, not detection).

### 3.2 Sweep rate and the Bright Data pool history (lines 39-72)
`TARGET_SWEEPS_PER_SEC=3.0` is the global polling rate against Target's RedSky inventory API. Security framing: this is the rate-limiting surface. History in the comments: on 09-04 a 403 "tarpit" was blamed on two app.py instances running at once (about 6 req/s) rather than on 3/s itself; the operator kept 3.0 as a stated requirement. Then a CAPTCHA wall appeared (F5/Shape, later identified as HUMAN/PerimeterX "Press & Hold") on the Bright Data (BD) proxy ranges. A home-IP sweep ran 09-04 to 09-07 and got zero 200s, which disproved the "IP-only" theory, so it was reverted on 09-07 to the 16-IP BD pool (3.0/s over 16 = 0.19/s per IP). `RESILIENT_HARVEST_VIA_LOCAL_IP=0` therefore means "sweep through BD exits". `RESILIENT_CAPTCHA_BACKOFF=1` means a captcha stops being hammered. Risk if wrong: burned IP reputation, which takes days of rest to recover (operator: stop the bot about 45 min before restart for burned IPs). Duplicate app.py instances double the effective rate; this is a blast-radius concern outside the file.

### 3.3 Probe verdict, parking, per-IP cap (lines 73-97)
09-07 probe: 3 of 4 pool IPs captcha, 1 clean, so the wall is IP-range reputation, not device. Changes: a captcha parks only that session (`RESILIENT_CAPTCHA_PARK_S=1800`, doubling to x8; the floor is 60 s so 0 is not an off switch), and the sweep is capped by usable sessions times a per-IP RPS ceiling. The 09-09 soak set that ceiling to 0.5/s (0.5/s = 293/293 clean; 2/s = HTTP 404 ban after about 166 reads, still blocked more than 3 min later; one IP still blocked 39 min after the burst). `RESILIENT_RAW_404_PARK_S=900` is the ladder base. Risk: too high a per-IP cap invites a multi-minute IP ban; too low a cap slows detection when few IPs are usable (single clean IP = 0.5 reads/s = up to 2 s detection latency).

### 3.4 The detection fix: app-channel (lines 98-106)
`RESILIENT_REDSKY_CHANNEL=apps_raw` reads the mobile-app endpoint (`/v1/apps/tcin_product_list_v2`) as raw HTTP with an iPhone app header set, instead of the in-page web fetch HUMAN captcha-walls. 09-09 probe through a walled exit: web = 403 captcha, apps_raw = 200. Security framing: the defender protects the web surface harder than the app API, and this switches surface. It also means the "browser" is a header-spoofed HTTP client; the app version string in `redsky_channel.py` (`2026.28.0`, iOS 26.4.1) is a hardcoded fingerprint that can go stale. Risk: if this var is lost, code defaults to `web` and the pool is captcha-blind. Kill: `=web`.

### 3.5 Log-only observability taps (lines 107-142)
`RESILIENT_206_LOG`, `RESILIENT_206_NOT_ERROR`, `RESILIENT_STATUS_LOG`, `RESILIENT_206_INGEST=shadow`, `RESILIENT_FLIP_LOG`. Born from 09-25 and 10-05 post-runs: RedSky answered 73-95 percent of sweeps with HTTP 206 at some points and the bodies were discarded (bodies held stock fields for 17 of 17 TCINs on 10-05). These taps log or shadow-compare only; nothing is ingested or purchased from a 206. `206_NOT_ERROR` (10-14) stops a 206 from counting toward the session-crash threshold. Risk: low (log volume; FLIP log capped at 50 lines per TCIN per run). Strategic note: 206 data is still unused for detection.

### 3.6 Canary off, fresh profiles off, tab-fetch fallback, trusted reader (lines 143-194)
- `STOCK_CANARY=0` (09-15): the canary was raw urllib from the home IP with mismatched TLS/UA every 30 s, "the exact bot-shaped hit HUMAN/Shape score". It was a self-inflicted detection signal; turned off.
- `RESILIENT_POOL_FRESH_PROFILES=0` (09-09 audit): wiping profiles did not help (all 16 sessions walled within 3.5 min); persistent profiles let HUMAN cookies age.
- Tab-fetch: only a browser that earned a valid Akamai `_abck` (the logged-in purchase profiles) could read RedSky when pool profiles were captcha-walled. `auto` makes that a fallback, engaging after 180 s of no pool 200. It reads through the PRIMARY purchase account's tab, so there is CDP contention and a risk to that account.
- `RESILIENT_TRUSTED_READER_PARK_S=600`: a captcha on the trusted browser parks that reader (protects the purchase account).
- Cadence 3-5 s: the REM contains a self-correction. It first argued 1-2 s was needed (wins land 0.4-3.7 s after a flip), then noted the reader never worked until fixed on 09-09 and that the home-IP browser tolerated only about 200 reads/h (18 s cadence) on 09-07; 1-2 s would be 10x on the primary purchase account, so 3-5 s "until the home IP's HUMAN budget is measured". The budget was apparently never measured in this range. Risk: 3-5 s is 720-1200 reads/h, 3.6-6x the only measured tolerated rate, on the account that places orders, though only while the pool is blind.

### 3.7 HUMAN Press & Hold guard (lines 195-208)
Context: when an account browser's trust score drops, the `/account` navigation shows a Press & Hold interstitial. The old ladder read it as a dead session and escalated (Chrome restart, sign-out, scripted relogin). The relogin was Shape-burned (0 of 12 usernames advanced, 09-06/07), leaving jars GUEST; business and alt-1 died that way. The guard takes a read-only DOM snapshot, parks the heavy rungs for 300 s, writes `[PX-CHALLENGE]` and `[AUTH_CRITICAL]` to `logs\error_log.txt`, and leaves the widget for a human to press. No automated solving. Security framing: this is credential-replay/relogin hygiene; repeated failed scripted logins are themselves a flag. Risk: unattended night with a challenge on screen = parked until a person acts.

### 3.8 Fingerprint and identity (lines 209-287)
History: 06-24 account_identity spoofed a stale Chrome 130 / macOS-on-Windows, an incoherent identity Shape flagged; spoof was disabled. 07-12 identity was rebuilt coherent (real Chrome 150 + Windows) and fingerprints re-enabled (`RELOGIN_SKIP_FINGERPRINT=0`, `TARGET_APPLY_FINGERPRINT=1`). Login stays on HOME IP (`RELOGIN_SKIP_PROXY=1`) because BD-IP login was Shape-blocked ("password did NOT advance"), re-confirmed 07-12. Purchases still exit each account's own BD IP. 09-08 `TARGET_SPOOF_JS=0`: JS prototype tampering (toString not native) is itself a tell for Shape and HUMAN and never unlinked accounts. 09-13 `TARGET_UA_MODE=engine`: the purchase tab sent a full-version UA ("Chrome/152.0.7977.82") and a brand list without GREASE, while harvest/warmup tabs sent the reduced UA, so a banked Shape sensor was minted under one UA and replayed under another. Now no UA override; the comment says `hand_login_all.bat` must set the same mode (not verified in this chunk). `TARGET_FP_CHROMIUM=0`: A/B results (08-21 to 09-03) showed fp-chromium 0 of 318 vs real Chrome 9 of 146 on the hot-SKU gate (Fisher p=2.5e-5, IP-range confounded), so all three accounts run real Chrome. The A/B then tests the IP axis: primary on HOME IP (proxy_url emptied in `config\target_accounts.json`), business 31.98.158.87, alt-1 168.158.32.64. The SKIP list and SEED_SALT are inert while the master is 0. Risk: with real Chrome, all accounts share one machine's hardware fingerprint (canvas/WebGL/audio), the very cross-account linker the 07-12 comment names. Operator's accepted trade-off.

### 3.9 TEST_MODE pin (lines 289-292)
`TEST_MODE=false` is forced so a stray `true` in the shell cannot turn a live run into a no-op. Safety-positive. Only the literal `true` (case-insensitive) activates test mode in the purchase manager.

### 3.10 Purchase retry tuning (lines 294-340)
- `TARGET_RETRY_WHILE_IN_STOCK_MAX=40` (06-30): a worker fired 24 ATC shots (all instant 429) and quit with about 38 s of its 110 s budget left; the cap is raised so the time budget (`TARGET_RETRY_WHILE_IN_STOCK_BUDGET_S`, default 110, not set in this range) is the binding limit. Pre-ATC 429s cannot double-buy.
- `TARGET_ATC_EDGE429_RETRY_DELAY_MIN/MAX=2.0/3.0` (08-26): tighten the sleep only after empty-body (edge) 429s, about 50 percent more tickets. The operator labels it a "doctrine bet", expected value approximately 0 on hyped SKUs. The 2.0 s floor is stated as at least 2x the vendor's roughly 1 s per-IP ban floor (competitor docs).
- `TARGET_ATC_RESPONSE_HEADER_CAPTURE`, `_RESP_HDRS`, `_RESP_LABEL`: log-only CDP interception of ATC responses (headers, Tgt-Cart-Error-Key, tab label). The label fix exists because warmup heartbeat shots (5,144) were counted alongside real shots (138), inflating shot volume up to about 40x in analysis. Risk: CDP response-stage interception sits on the purchase critical path ("continue exactly once", never mutates), a nonzero latency/behavioural surface; the sorted-header log could leak identifiers (Set-Cookie names only, values suppressed).

### 3.11 ATC gate-wall circuit breaker (lines 341-394)
A breaker (08-09) counted consecutive carts-service denials per identity+TCIN and, past a limit, throttled the retry loop. Loosened 08-18 (8/120 to 20/45), then turned OFF 08-31 after an audit showed it cut cadence from 48/min to 3.2/min for 18 min of live stock (about 980 forgone shots) with 245 arms and zero followed by a 2xx. Operator's finding: the hot-SKU 401 re-forms in 45-95 s at any cadence and resting does not lower it. The remaining `set` lines (STREAK_LIMIT, COOLDOWN, COUNT_EDGE_429, TTL) are retained but inert. Conclusion in comments: shot count is the only lever against a global edge demand lottery. Risk (the other side of the bet): with the breaker off, a genuine identity-hardening wall is hammered at full cadence. The 08-09 note says "continuing to hammer ACCELERATES the block"; the operator later judged the evidence did not support it.

### 3.12 In-place checkout re-shoot (lines 395-406+)
07-17 drop: ATC 201 three times, but every checkout POST was 429 FAST_SELLING_ITEM_RATE_LIMIT_EXCEPTION. Now the place-order POST is re-fired in place up to 4 times (about 3 s apart, fresh Shape token) before clearing the cart. Double-buy safety: re-shoots only while status stays 429/424 and stops when an order_id lands. This is the one flag in the range with money-safety implications. Continues into the FAST LANE section after line 410.

## 5. Comment vs code drift

1. **Code defaults differ from the bat**, so removing a line silently changes behaviour: `RESILIENT_PER_IP_MAX_RPS` code 1.0 vs bat 0.5; `RESILIENT_RAW_404_PARK_S` code 120 vs bat 900 (the comment's measured 15-min base requires the bat); cadence code 1-2 s vs bat 3-5 s; `RESILIENT_REDSKY_CHANNEL` code `web` (captcha-walled per the comments); `TARGET_ATC_RESP_HDRS`/`_RESP_LABEL` code 0 vs bat 1; `TARGET_UA_MODE` code `legacy` vs bat `engine`; `STOCK_CANARY` code on vs bat off; `TARGET_RETRY_WHILE_IN_STOCK_MAX` code 24 vs bat 40. The bat is the only thing arming the "detection fix" (apps_raw).
2. **Lines ~76-86:** comment says "a lone clean IP is read at 1/s (validated ceiling), never 3/s"; the later 09-09 note and the bat value say 0.5/s. The 1/s statement is superseded, not corrected in place. Code default is still 1.0.
3. **Lines ~39-50:** the reasoning that 1.5/s "halves RedSky load" is history; value is 3.0. "Revert: 3.0" describes a revert that was already applied.
4. **Cadence block (lines 180-194):** the first paragraph argues for 1-2 s ("Widen toward 4s if home IP shows a burst flag"), then the "09-09 CORRECTION" sets 3-5 s. The code docstring (app.py near 1270) still argues for 1-2 s with code defaults 1.0/2.0. Two contradictory rationales exist; the active value follows the correction.
5. **Lines 209-235 fingerprint block:** "Rollback (re-enable spoof): delete these three SET lines" is stale: the three lines now carry the opposite meaning (0/1/1), so deleting them does not roll back anything; the 07-12 rollback text is the current one.
6. **Gate breaker block (lines 341-394):** reads as an active protective feature (08-09, 08-18 "20/45 still brakes a 2,960-add runaway") but the effective state is OFF (08-31). The comment accurately says the code default is also off (confirmed, purchase_executor.py:1941). However the STREAK_LIMIT/COOLDOWN lines are inert, and code defaults for those are 8/120 (the "protective" values), so a bare enable without the bat's 20/45 would use 8/120.
