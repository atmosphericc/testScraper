ROOT CAUSE — INVALIDSTATEERROR + UN-APPLIED PATCH
================================================================================

zendriver/core/connection.py Transaction.__call__ takes a CDP response and
calls self.set_result() / self.set_exception() on the transaction's asyncio
future. If the future is already done (client-side timeout cancelled it, or
a duplicate response arrives), set_result raises asyncio.InvalidStateError.

In the listener_loop, the response-dispatch branch calls tx(**message)
UNGUARDED, so that exception propagates and kills the listener_loop task
for the browser connection. From that point, no CDP response is delivered
to any awaiting coroutine. Every tab.evaluate(), tab.get_all_cookies(),
etc. hangs forever — the event loop is alive but every task on it is
blocked on an await that will never complete.

The 2026-05-21 incident produced the same failure mode. On 2026-05-22,
patch_zendriver.py was created to inject `if self.done(): return` at the
top of Transaction.__call__. The script ran on 2026-05-22 against the venv
of that day. But the venv on disk today was NOT patched — pre-fix line 118
of connection.py read straight into the `if "error" in response:` check
with no guard. Either the venv was rebuilt between 5/22 and 5/24 (pip
install / requirements update), or the patch was run against a different
venv path. Either way: the May 24 venv was vulnerable, and the bug was
re-armed.

The placeholder TCIN 1011467802 ("Product 1011467802 (new TCIN -
unverified)") in config/product_config.json supplied the trigger. Target's
product_summary_with_fulfillment_v1 endpoint returns a 200 with an embedded
`errors` array for unknown TCINs in a batched query. zendriver's CDP
deserializer encounters this partial-error shape during fetch result
parsing, the Transaction future hits an edge case (likely the read-timeout
race in tab_dispatcher), and the listener_loop dies.

WHY THE TERMINAL WAS FROZEN: a combination of three factors —
  1. shutdown_handler relies on print() and on coroutines that await on
     the dead event loop (sm.save_session_state via run_coroutine_threadsafe).
     With timeout=2 the coroutine call should return fast, but print() goes
     through a teed sys.stdout that writes to BOTH the console AND the run
     log. If the console buffer wedges (mark mode, scroll-lock, or
     saturation from the 238 multi-KB tracebacks), print blocks the signal
     handler itself.
  2. On Windows, signal.signal(SIGINT) only sets a flag the interpreter
     checks between bytecodes. The main thread is inside waitress.serve(),
     which does its own select() — signal pickup is not instantaneous.
  3. The wrapper .bat sits in `ping 127.0.0.1 -n 11` between relaunches;
     the user's Ctrl+C went to the .bat first, which then prompted
     "Terminate batch job?". Answering Y kills the batch but does NOT
     reliably terminate the already-detached python child. Force-kill
     via Task Manager was the only escape.


FIXES APPLIED THIS REVIEW
================================================================================

FIX 1 — RE-APPLY ZENDRIVER PATCH TO VENV
    Ran patch_zendriver.py against .venv. connection.py now contains the
    `if self.done(): return` guard at the top of Transaction.__call__.
    Verified by re-reading lines 110–134 of connection.py.

FIX 2 — REMOVE INVALID TCIN 1011467802
    Deleted the "Product 1011467802 (new TCIN - unverified)" placeholder
    entry from config/product_config.json. Down from 24 → 23 products,
    last TCIN is now 94300072. This eliminates the trigger that fed the
    InvalidStateError storm.

FIX 3 — IN-PROCESS RUNTIME GUARD IN app.py
    Added a runtime monkey-patch in app.py alongside the existing sameParty
    patch (lines ~166–183). At import time it wraps
    zendriver.core.connection.Transaction.__call__ with a `if self.done():
    return` guard. This is belt-and-suspenders: if the venv source patch
    is ever lost again (pip install zendriver --upgrade, fresh venv,
    requirements.txt rebuild), the runtime patch still protects the
    listener_loop. Verified the patch with a standalone smoke test.

FIX 4 — DEADMAN SWITCH IN shutdown_handler
    Added a daemon thread to shutdown_handler (app.py ~3960) that sleeps
    15 seconds and then calls os._exit(2) regardless of what the rest of
    the handler is doing. If the cleanup path wedges for any reason
    (blocked print, hung run_coroutine_threadsafe, stuck file write),
    the process is guaranteed to exit within 15s of the first Ctrl+C.
    The deadman writes its banner with os.write(2, ...) directly to fd 2
    so it cannot itself block on a wedged sys.stderr.

REMAINING RECOMMENDATIONS (not applied this review)
================================================================================

R1 — RUN patch_zendriver.py FROM THE WRAPPER .BAT
    Add a line near the top of run_bot_with_nightly_restart.bat:
        "%PYTHON%" patch_zendriver.py
    This makes the patch idempotently re-applied on every launch, so a
    quiet pip operation between runs cannot regress the venv. The
    in-process FIX 3 covers the same gap but defense-in-depth is cheap.

R2 — CONFIRM-OR-DELETE THE WRAPPER BATCH MORNING-Y HABIT
    The user's "press Y to terminate batch job" answer kills the .bat
    but the detached python child may survive. Either:
      (a) Make the .bat use `start /WAIT /B` so Ctrl+C propagates to the
          child cleanly, or
      (b) Move stopping to a single command:
          taskkill /F /IM python.exe /T  (in addition to or instead of Ctrl+C).

R3 — DISABLE WINDOWS CONSOLE "QUICK EDIT" MODE FOR THE BOT WINDOW
    Quick-edit mode + an accidental click in the console window puts the
    console into a "mark/select" state that BLOCKS the process on its
    next stdout write. With 238 multi-KB tracebacks flying past, the
    chance of an accidental click was high. Right-click the cmd window
    title bar → Properties → Options → uncheck "QuickEdit Mode". The
    deadman switch (FIX 4) covers this case from the other end, but
    eliminating the trigger reduces wasted runtime.

R4 — SUPPRESS THE FULL RESPONSE BLOB IN ASYNCIO ERROR LOGS
    Each InvalidStateError currently dumps the full GraphQL response
    (~5–10 KB per traceback) because the StopIteration value contains
    the RemoteObject(value=...) payload. With the guard in place these
    will no longer fire from this cause, but if a future regression
    surfaces, we should install an asyncio exception handler that
    truncates the value to ~200 chars before logging. This is also
    cheap insurance against the console-buffer saturation that may
    have helped wedge the terminal on 5/24.
